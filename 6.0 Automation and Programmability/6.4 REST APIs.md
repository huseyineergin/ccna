# 6.4 REST APIs
## Introduction
An **API (Application Programming Interface)** is a software interface that allows two applications to communicate with each other.
- APIs are essential not just for network automation, but for all kinds of applications.
- In SDN architecture, APIs enable communication between applications and the SDN controller via the NBI, and between the SDN controller and network devices via the SBI.
- The NBI typically uses REST APIs.
- NETCONF and RESTCONF are popular southbound APIs.
## CRUD Operations
CRUD operations are the four basic operations used to manage data in a database or software application.
- The four basic operations are:
	- **C (Create)**: Add new data or records.
	- **R (Read)**: Retrieve or view existing data.
	- **U (Update)**: Modify existing data.
	- **D (Delete)**: Remove existing data.
- HTTP uses verbs (aka. methods) that map to CRUD operations.
- REST APIs typically use HTTP.

|              Purpose              | CRUD Operation | HTTP Verb  |
| :-------------------------------: | :------------: | :--------: |
|       Create new variable.        |     Create     |    POST    |
|  Retrieve value of the variable.  |      Read      |    GET     |
| Change the value of the variable. |     Update     | PUT, PATCH |
|         Delete variable.          |     Delete     |   DELETE   |
## HTTP Request
An HTTP request is a message sent by a client, such as a web browser, mobile app or another program, to a server to ask for information or perform an action.
- When an HTTP client sends a request to an HTTP server, the request includes information such as:
	- An HTTP method (verb).
	- A **URI (Uniform Resource Identifier)** identifying the resource being accessed.
- The HTTP request can include additional headers that provide information to the server.
	- For example, an `Accept` header informs the server about the types of data the client can accept in the response.
		- `Accept: application/json` or `Accept: application/xml`.
## HTTP Response
An HTTP response is a message sent by a server back to a client after the client makes an HTTP request.
- The server’s response will include a status code indicating if the request succeeded or failed, as well as other details.
	- **1XX Informational**: The request has been received, understood and is being processed.
		- 102 Processing: The server has received the request and is processing it, but the response is not yet available.
	- **2XX Success**: The request has been received, understood and accepted.
		- 200 OK: The request succeeded.
		- 201 Created: The request succeeded and a new resource was created as a result.
	- **3XX Redirection**: The client must take additional action, usually a URL redirection, to complete the request.
		- 301 Moved Permanently: The URI of the requested resource has been changed permanently.
	- **4XX Client Error**: An error appears to have been caused by the client.
		- 401 Unauthorized: The client must authenticate itself to get the requested response.
		- 403 Forbidden: The client does not have access rights to the content; that is, it is unauthorized.
		- 404 Not Found: The requested resource could not be found.
	- **5XX Server Error**: The server has encountered an error or is unable to perform the request.
		- 500 Internal Server Error: A generic error message, given when an unexpected condition was encountered and no more specific message is suitable.
## REST (Representational State Transfer)
REST is an architectural style for designing web services and APIs. It defines principles for how systems communicate over a network, typically using HTTP.
- REST isn’t a specific API. It describes a set of rules about how the API should work.
- REST APIs are also known as **REST-based APIs** or **RESTful APIs**.
- For applications to communicate over a network, networking protocols must be used to facilitate those communications.
	- For REST APIs, HTTP(S) is the most common choice.
- The six constraints of RESTful architecture are:
	- **Uniform Interface**:  Resources are identified by URLs, and standardized methods and representations provide a consistent way to interact with them.
	- **Client/Server**: The client handles the user interface, while the server manages application logic and data. They can evolve independently.
	- **Stateless**: Each request must contain the information necessary to process it. The server does not rely on stored client-session context from previous requests to understand the current request.
	- **Cache**: Responses should indicate whether they can be cached. Caching suitable responses can reduce latency and server load.
	- **Layered System**: The client may communicate through intermediaries such as proxies, gateways or load balancers without needing to know the full system architecture.
	- **Code on Demand (Optional)**: A server may send executable code to a client, such as JavaScript.
## Types of REST API Authentication
### Basic Authentication
Basic authentication is a simple method of authenticating API requests using a **username** and **password**.
- A username and password are included in the HTTP headers.
	- The username and password are included in the HTTP `Authorization` header.
- The username and password are sent in the format `username:password`, **encoded in Base64**.
- **Advantages**:
	- Simple and easy to implement.
- **Disadvantages**:
	- Since credentials are sent in every request, attackers could steal them if the connection is not properly secured.
	- Even if using HTTPS for encryption, relying solely on a username and password combination is not particularly secure.
### Bearer Authentication
Bearer authentication is a method of authenticating API requests using an **access token**.
- The client first obtains a token by authenticating with an authorization server.
	- This can be done using using basic authentication or another method.
- For each API call, the client includes the token in the HTTP `Authorization` header.
- The term **bearer** means that anyone who possesses the token can use it.
	- If an attacker steals the token, they can make API calls as if they were the legitimate user.
	- To mitigate against this, tokens **expire** after a set period of time.
- **Advantages**:
	- More secure than basic authentication.
	- Tokens expire, so a stolen token is only valid temporarily.
- **Disadvantages**:
	- If a token is stolen, an attacker can access the API until the token expires.
	- Tokens must be refreshed periodically, adding complexity to implement.
	- Should only be used with HTTPS.
### API Key
API key authentication is a method of authenticating API requests using a unique key issued to a client or application.
- It uses a **static key** issued by the API provider.
	- The client uses this key in each API call for authentication
	- Unlike bearer tokens, the API key is static and remains valid until revoked.
- API keys can be sent in various ways:
	- In the HTTP `Authorization` header.
	- In the URL. (e.g, `?api_key=key`)
		- This is not recommended because URLs are often logged by web servers, proxies and browsers.
	- In a cookie.
- **Advantages**:
	- Easier to implement than bearer authentication.
	- Useful for tracking API usage and often used by cloud services and third-party APIs.
- **Disadvantages**:
	- If stolen, the key grants full access until revoked.
	- API keys must be rotated manually to maintain security, whereas tokens expire automatically.
### OAuth 2.0
OAuth 2.0 is an **authorization framework** that allows an application to access resources on behalf of a user or application without requiring it to share the user's password with the resource service.
- It provides **access delegation**, granting third-party applications **limited access** to resources.
- The four main roles in OAuth 2.0 are:
	- **Resource Owner**: The person or entity that controls the protected data.
	- **Client**: The application requesting access.
	- **Authorization Server**: Issues access tokens after the required authorization process.
	- **Resource Server**: Hosts the protected API or data.
- The OAuth 2.0 authentication and authorization process consists of six steps:
	1. The client application requests authorization from the resource owner to access the resource.
	2. The resource owner grants authorization by signing in to their account and giving permission.
	3. The client application exchanges the authorization grant for an access token from the authorization server.
	4. The authorization server issues an access token to the client application.
	5. The client application sends the access token to the resource server to request the resource.
	6. The resource server validates the access token and provides the requested resource to the client application.
- The access token functions just like the token used in bearer authentication.
	- It grants access to the specified resource within the permitted scope.
	- Access tokens expire after a short period, but OAuth 2.0 uses **refresh tokens** to obtain new access tokens without requiring the user to sign in each time.
